# Next investigations after E06

These are prepared investigation designs. No CPU scheduling, paging or engine replacement is enabled by this file.

1. **CPU helper scheduling.** The pinned Apple branch in `ggml-cpu.c` retains inherited scheduling at normal priority. Its higher priorities use `pthread_setschedparam`/FIFO, and Apple affinity masks are unsupported. First measure the helper workers' actual QoS in an isolated diagnostic build. If they are already user-initiated or better, park the idea. Otherwise test public Apple QoS for helper workers only, not realtime/FIFO scheduling. Require actual successful dispatch evidence, unchanged target/model math, full token parity, normal pressure/zero new swap and fresh ABBA English code/prose. Ordinary profiles remain unchanged until confirmation. No percentage is estimated yet.

2. **Native CPU/GPU submission stalls.** One E06 JSON response runs at80.14TPS while median GPU clock remains1618MHz, thermal state is nominal, and other CPU load is low. This rules out neither CPU scheduling nor short GPU/driver stalls; one-second device averages cannot expose sub-second waits. Next isolate helper evaluation, CPU gather and GPU completion-wait envelopes on the kept stack, with an untraced control to measure observer overhead. Keep trace timings separate from speed qualification. Preserve the outlier and all closing controls.

3. **Bounded Apple lookup prefetch.** E03's first long-input CPU lookup envelope crossed its investigation threshold; warm P06 remains screened low benefit. The current Mac branch has no active `llama_prefetch` platform implementation. E06 now observes process page-in increments in some larger-chunk windows without new swap, which supplies a way to compare a bounded candidate but does not establish an SSD bottleneck. Start with mapping/row-range bounds and advice-return/physical residency proof, then isolated first-exposure/replay controls. No whole-file warming, cache purge inside brackets, raised memory cap, or transferred disk-speed percentage. See [upstream30405](https://github.com/ggml-org/llama.cpp/pull/30405).

4. **Separate MLX capacity/quality trial.** A new October13 documentation commit records actual M5 Pro64GB owner results and layer-at-a-time/read-ahead comparisons. That is useful platform evidence, but IQ3_S partially resident and IQ3_XXS/BF16-helper figures are not our48GiB residentQ2/sharedQ3 benchmark. Main's new commit is documentation only. Before a trial, budget target/helper and dense activation conversions together, inspect Q2/helper support, pin its code and dependencies separately, and qualify memory and English outputs before comparing speed. Preserve strict/default precision differences and model-specific constraints. [New report](https://github.com/yibie/strata-mlx/issues/8), [documentation commit](https://github.com/yibie/strata-mlx/commit/2f11ab3e752adc84525d82c75d598b5898f96060).

5. **Interrupted-conversation caching remains secondary.** The same64GB report has much faster return to parked conversations with a4GiB cache. Our app already caches a live prompt. A multi-conversation cache needs separate retention, cancellation, eviction, memory and privacy checks; its memory budget may outweigh the benefit here. It does not improve first-time generation TPS. Keep it behind the CPU/prompt investigations above.

All future speed results must separate first exposure, learned draft-cache replay and new questions, use complete normal-EOS replies, retain failures, and score each candidate against its own repeated controls. Small validated gains are eligible; source or workload changes alone are not gains.
