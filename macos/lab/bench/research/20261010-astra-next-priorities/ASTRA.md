### 1. R08 is the best next native question, not a proven optimization

Live local `src/llama-context.cpp:1428` only reuses a graph if `gf_res_prev_active == res` and graph parameters match. `get_gf_res_prev()` at 2475 selects one of two arenas using `n_outputs > 0`. On a miss, lines 1438–1464 reset the graph and scheduler, build the model graph and allocate it. The helper alternates no-output target catch-up and output-producing draft steps. This is a real source mechanism; the actual exposed delay in the current P07 workload is still unmeasured.

Do not just delete the active-arena check. The scheduler can have replaced allocations and tensor-copy state. A valid solution needs stable bounded allocation ownership, complete keys for token/sequence/output/pool topology, invalidation for memory changes, safe input rebinding and synchronization that does not undo the saving. Start with the helper, not a general graph cache.

The old [Metal graph reuse PR #14570](https://github.com/ggml-org/llama.cpp/pull/14570), head `bf8b39015fdf82c0beac9ebdeb9534a825c2fb4c`, explicitly found its Metal encoding cost already hidden by CPU/GPU overlap. That is a warning about measurement, not a disproof of this higher-level alternating scheduler path. Do not label unaccounted phase-trace time “planning.” Keep fusion on; tensor callbacks can destroy the behavior being measured.

Let `p` be the fraction of whole-reply time demonstrably exposed in the removable path and `r` the fraction actually removed. The reply-time reduction ceiling is `p*r`; throughput increase under a fixed amount of output is `1/(1-p*r)-1`. Even 1% exposure can justify cheap exact work; there is no inherited 2% minimum. If the exposed ceiling is below measurement resolution or almost entirely overlapped, park R08 before implementing a complex cache.

### 2. R09 uses the M5 GPU realistically

The M5 **GPU Neural Accelerators** are matrix units inside GPU cores. They are distinct from the separate **Apple Neural Engine**. Metal TensorOps can reach the GPU units; Core ML/Neural Engine conversion is a separate runtime project. Apple documents the distinction and custom cooperative-input dequantization in its [M5 Tech Talk](https://developer.apple.com/videos/play/tech-talks/111432/) and [WWDC26 session 330](https://developer.apple.com/videos/play/wwdc2026/330/). Tensor API is already on locally; it is not an untapped switch worth claiming as a new gain.

The specific remaining hypothesis is eliminating the existing Q2 unpack-to-threadgroup staging by loading compatible cooperative input fragments directly, while retaining the same stored bytes and mathematical operations. New native MX formats are not the GGUF Q2_0 format. Reinterpreting Q2 as MXFP4/INT4, reducing intermediate precision or changing accumulation grouping is not an exact port. The coordinator verified the installed SDK exposes `get_left_input_cooperative_tensor`, compatibility checks and right-input counterparts; this is header evidence only. No compile, layout, actual accelerator occupancy or precision proof was performed.

The initial candidate should keep the current 32-row tile and original loop/reduction order. Do not reintroduce U10-02's rejected 16-row dispatch, P11/P12 compact scheduling, P10 route-map reuse or P09 split-K. Use a tiny compile/layout/precision probe first; exact full expert-block fixtures precede performance. Test representative T32/127/508/512 shapes, valid real/skewed/distinct routes, unsupported strides and complete gate/up/activation/down/reduction consumers. Retain input/weight digests. If exact arithmetic cannot be maintained, stop the keeper-track proposal rather than relaxing its rule.

The BaseRT paper supports this compute-versus-memory distinction, not a 6.4× forecast for Flash. Its default-engine baselines and Q4/Q8 converted models differ from our tuned Q2 path. MLX #3018's large dense split-K thresholds likewise do not fit ordinary few-row verification. In current long P07 controls, TTFT is about 23–25% of a roughly 7.2-second capped reply: even an 8% faster entire prompt phase saves only about 1.7–1.9% of that reply in a simplified unchanged-decode calculation. A single improved kernel would generally save less; measure the complete reply.

### 3–4. Speculation savings must preserve the tested state machine

`common/speculative.cpp:1571–1611` constructs helper catch-up rows from target hidden states for the full target batch. Existing server flow performs this before final acceptance. Deferring that work and replaying only committed rows is distinct from shortening the target verification batch. But it changes helper shapes and state transitions. Matched token IDs alone do not make target hidden states interchangeable with helper-generated hidden states. First obtain per-cycle row counts, accepted prefix, target/helper work and overlap. Qualification must cover every accepted-prefix length, pending/verification hidden rows, helper KV/indexer/recurrent state, EOS, cancellation, restore and the exact extended fixture that failed D02 at token 228. Do not begin an adaptive-cap retry under this name.

Speculative-decoding theory guarantees the target distribution only under its algorithmic assumptions; it does not guarantee identical finite-precision execution after changing graph shapes or RNG consumption. [Leviathan et al., v2 May 18, 2023](https://arxiv.org/html/2211.17192) is useful for the draft-cost/acceptance tradeoff, not a waiver of these native gates.

W02 already proved small real throughput savings. Its newest prose worst launch-pair startup regression is 12.660 ms against a frozen 10 ms ceiling. Preserve that failure. A worthwhile reopening requires a measured first-token-path cause and a materially changed implementation, or a separately authorized, prospectively declared tradeoff profile. Moving a warmup outside the measured interval or rerunning until the number drops below 10 ms is not a fix. W02 is not among the immediate three stages until that cause is identified.

### 5. F32 KV is reasonable for the MLX screen; 34 GiB is not disproven

**Keep F32 for the first precision-matched numerical diagnostic, and separately test the ordinary F16 profile later.** The current MLX run uses F32 parameters/activations; its attention caches inherit key/value dtype, and its indexer keeps incoming dtype. Native F32 KV removes one intentional storage-rounding difference. It does not make all native intermediate arithmetic, attention algorithms or recurrent state equal to MLX, and is not by itself app parity.

F32 is not logically required merely to ask whether two token streams happen to agree. It is useful to interpret a disagreement. Native F16 versus MLX F32 would be a valid explicitly mixed-precision compatibility screen, but would add an avoidable confound. The ordinary app ultimately needs its own F16 comparison regardless of the F32 result.

The [recent native allocation log](../../results/20261010T071832Z-m5-stack-v2-p07-long-safety-1-conv-direct/server.log) reports at 4K F16: target attention KV 96 MiB plus indexer KV 24 MiB. The indexer constructor uses the same cache types. Scaling these allocations to context 512 gives approximately **15 MiB F16 versus 30 MiB F32**, a **15 MiB difference**. Alignment/implementation must be checked in the eventual actual log. This cannot solve a roughly 0.27 GiB admission deficit. Recurrent F32 state and the tens of GiB of model weights are separate; lowering KV precision does not halve them.

The helper-off/512/batch32 diagnostic does have a smaller budget than everyday P07. Removing helper-specific weights/repacking, helper compute/KV buffers and speculative rollback slots may matter far more than F16 versus F32. Source shows recurrent allocation scales with `mem_size*(1+n_rs_seq)`; ordinary depth-three logs hold 450.28 MiB versus an inferred 112.57 MiB at zero rollback snapshots. The inference depends on actual helper-off resolved parameters and is not a measured memory saving. Helper mapped/repacked buffers may share or replace physical pages; do not blindly sum their logged sizes as recoverable RAM.

Conversely, the same log still maps about 35.28 GiB of first-shard model buffers, plus a separately lazy 26.82 GiB lookup mapping. A mapping is not residency. [A recent P07 candidate](../../results/20261010T072014Z-m5-stack-v2-p07-long-safety-2-small-reduce/result.json) began with 38.204 GiB available and reached 2.016 GiB, zero new swap. Its peak RSS is not total unique unified-memory occupancy. These receipts do not establish that the current 33.729 GiB available is safe for the unmeasured helper-off profile, nor that a 34 GiB gate is unnecessarily strict.

**Judgment:** the inherited 34 GiB rule is a reasonable hold, but not a validated profile-specific capacity model. Do not lower it to the observed free number or claim a safety margin from arithmetic alone. Build a profile ledger for first-shard residency, helper ownership, recurrent slots, both KV caches, compute/output arenas, checkpoint payloads, first-touch transients and other host use. Retain zero-new-swap, normal pressure and healthy monitoring. Preserve the native 1 GiB floor and separate MLX 8 GiB floor; do not transfer floors between engines. If a later new admission proposal is justified, preregister it separately with uncertainty/margin and a bounded capacity validation under explicit run authorization. No proposal or guard is changed by this report.

For cross-engine numerical qualification, use teacher-forced common token histories so divergence does not immediately change the next input. Compare final logits/top-ranked margins and mapped semantic state at specified positions; differing cache layouts require an explicit transform. Select tolerances before the run from a justified numerical reference/precision analysis, not after inspecting disagreement. No universal `1e-5` promise is defensible here. First-difference token, logits, layer/state location and dtype remain evidence even when outputs differ. A short greedy token match qualifies only that screen; sampled output, API/SSE, cancellation, continuation, longer context and complete-answer quality are separate stages.

### 6–8. Deferred work retains a concrete reopening condition

R05 remains held for the exact reason in its existing card: removing payloads can break a later cache-enabled request, while skipping checkpoints can change prompt splits and arithmetic. The local long-prompt log still shows 112.571 MiB checkpoints, but bytes do not establish exposed copy cost. Reopen for a measured serialization bottleneck and a lifetime-safe implementation or explicitly separate stateless-only contract. The open upstream PR does not solve our full exact-history requirement by itself.

MLX 16 decimal GB would add at most a nominal 4e9 bytes, **3.725 GiB**, of expert budget over 12 GB. Subtracting that from the observed 13.340 GiB host minimum yields roughly 9.614 GiB—only an arithmetic scenario, not a fit guarantee above the 8 GiB floor. OS file cache, transient arrays, eviction/readback behavior and host variation can change the result. There is no justified 16 GB TPS estimate: misses already fell sharply at 12 GB, but logical byte counts are not exposed SSD wait or hardware bandwidth.

If a slower low-memory engine is valuable, first qualify the numerical bridge and independently confirm 12 GB in a new immutable campaign. Then a new 12/16/16/12 comparison can answer the new cache question. Use the same F32/greedy/helper-off exact-token/finish/state scope, fixed excluded warmups, three measured English answers per workload per launch, empty store at launch, warm store within launch, fresh memory gate and unchanged 8 GiB floor. No mid-comparison cache purge or service closure. Keep cold load separate from warmed generation; do not call an OS-cached logical read a physical SSD read. A confirmation is labeled confirmation, not another new gain.

MLX draft/resident/F16 pathways are a later engine-evaluation program. Its default F16 changes near-tie outputs in the author's tests; its separate draft model is not our packed shared Q3 helper; the new fit calculator is not an F32 memory model. Changing these together would confound both quality and speed. An eventual matched native-versus-MLX helper-off cohort could quantify an actual ratio. Today's 60/40 versus 14.5/15.7 figures demonstrate why the new alternative is not ready to replace the app, but are not a controlled native speed ratio.

## The next three sequential tests

These are proposed stages to authorize later. No automatic run is queued. Each stage stops on a failed prerequisite; a hard resource rejection is not followed by an unchanged retry.

1. **P07 bottleneck diagnostic, preceded by the load-free profile budget audit.** First finish the two explicit allocation ledgers: ordinary P07 and helper-off F32/512/32. This can progress while native admission is unavailable. Under a later authorized healthy launch meeting the existing guard with margin, compare uninstrumented P07 to a narrowly instrumented same-source build and back to uninstrumented. Use the existing English short code/prose, 256-output cap, and long code/prose cohort separately. Capture graph arena/key/miss counters, CPU build/reset/allocate/input spans, normal GPU command times, helper catch-up rows/acceptance and checkpoint spans. No per-tensor callbacks, disabled fusion, artificial sync or inference from trace remainder. Require identical outputs and unchanged request topology; quantify instrumentation perturbation. Deliver exposed fractions and Amdahl ceilings, **not a TPS improvement**. Park mechanisms whose plausible removable cost cannot justify their complexity/noise.
2. **One R08 native candidate if stage 1 exposes reusable work.** Implement a bounded helper plan/ownership mechanism over current P07, all other features unchanged. First exact component/state histories, including cancellation/restore/rollback and D02's extended fixture. Prove the intended cache hits under normal execution and bound additional memory. Then fresh P07/candidate/candidate/P07 launches, excluded fixed warmups, three measured English code/prose answers per launch, followed by one independent confirmation bracket only if it qualifies. Measure generation, client first content and capped reply separately. Include complete-to-EOS held-out English tasks with an adequate fixed maximum and report truncation/quality explicitly; do not pool them with capped throughput. Long prompts, short replies and cached continuation are separate safety cohorts. **If stage 1 shows no useful exposed R08 work, do not build this cache; advance to stage 3.**
3. **R09 eligibility and exact component trial.** First compile-only probe of the installed cooperative-input API and precision/layout contract; then exact full expert-block fixtures. Keep Q2 bytes, precision, 32-row geometry and original reductions; no P11/P12/P10/U10-02 mechanisms piggybacked. Only a valid complete-block benefit earns a native long-prompt TTFT/reply test. If it loses or cannot preserve required arithmetic, park with source/fixture reason. This is a prompt-latency investigation, with no expected ordinary decode gain.

This order deliberately leaves the new MLX 16 GB cache outside the next three speed stages. A blocker in native memory admission permits load-free design/eligibility work; it is not a reason to relabel MLX capacity progress as native speed progress.

## Comparison rules for small gains

- Freeze source/build/model/dependency/runner identity, English inputs and token IDs, sampler/seed, helper settings, context, cache policy, output budget and resource gates before timing. Current keeper P07 is the fresh control; do not compare only against older `conv-direct` or add older gains.
- Retain fresh two-launch-per-arm ABBA structure and per-launch medians. Both candidate medians must beat both controls; improvement must exceed twice that metric's own control drift. There is **no fixed 1%, 2% or 3% minimum**. A new plan may add preregistered uncertainty analysis, but not treat within-launch requests as independent process samples.
- Qualify the claimed metric and complete reply, with no material first-content, generation, cached-behavior or memory regression. Preserve contemporaneous gates, especially W02's 10 ms failure; a new tradeoff policy must be explicit before new results.
- Require exact native outputs/finish conditions and relevant cache/rollback/state checks. Cross-engine numerical tolerances are a separate justified protocol, not permission to relax a native exactness rule.
- Normal pressure, zero new swap, reliable monitoring and fresh launch headroom remain required. Record native allocations and host memory alongside RSS. Use physical I/O evidence before an SSD attribution.
- One bounded screen and, for a qualifier, one fresh confirmation; preserve excluded runs and stop on unexplained divergence. Do not cherry-pick prompts, controls or thermal intervals, or combine passing fragments from rejected campaigns.
