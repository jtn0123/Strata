# Astra: next speed experiments for the 48 GiB M5 Pro

Research snapshot: October 9, 2026, checked through 12:18 UTC. This is source research and analysis of existing results. No builds, model loads, GPU tests, installations, service changes, commits, pushes or PRs were performed. This report is the only file written by this investigator. Existing dirty and untracked work was preserved.

**The best next small experiment is to extend Metal's existing MoE weighted-reduction fusion from eight to ten selected experts.** The current model selects ten, and both our pinned engine and today's upstream have an eight-expert limit. Two other worthwhile experiments are the new upstream consolidated sampling-output read and a shape-specific BF16 projection kernel informed by MLX's October 8 thin-matrix implementation. These are testable opportunities, not established additional speedups.

The larger expert-kernel ideas are still useful, but the evidence now favors a bounded sequence: remove a specific missed fusion; measure redundant synchronization overhead; then optimize one exact shared projection shape. Do not combine their estimated gains or promise another percentage from someone else's machine.

## Ranked experiments

All low/base/high numbers are **hypothesized local relative improvements**, chosen to budget experiments. They are not measurements, confidence intervals, expected compound returns or transferred published results. Negative numbers mean a possible regression. Unless marked otherwise, the metric is sustained fresh-output TPS at the current depth-three setting. Whole-reply benefit depends separately on prompt time and answer length. Confidence describes whether this is a worthwhile experiment, not confidence that its base gain will occur.

The following details explain the source match, cheapest useful test and reasons to stop each experiment. Targeted kernels and bounded row prefetch were already queued themes; the new contributions here are exact missing patterns, fresh kernel designs and applicability checks, rather than presenting those themes as new discoveries.

**1. Extend the existing weighted reduction to ten experts.** Plain-language benefit: combine ten expert answers in one GPU pass, avoiding intermediate weighting and addition passes. Our graph emits a MUL, ten VIEWs and nine ADDs in [`llama-graph.cpp:2371`](../../vendor/llama-m5-copy/src/llama-graph.cpp). The existing matcher allows only 2-8 experts and its pattern table stops at eight; [`ggml-metal-fusion.h:23`](../../vendor/llama-m5-copy/ggml/src/ggml-metal/ggml-metal-fusion.h) caps raw fusion length at 16, while ten experts need 20 raw nodes. The generic reduction shader already accepts a function-constant expert count. [Pinned current upstream matcher](https://github.com/ggml-org/llama.cpp/blob/609290be6b15db02f9d73443435403cbff6e7802/ggml/src/ggml-metal/ggml-metal-fusion.cpp#L503), [shader](https://github.com/ggml-org/llama.cpp/blob/609290be6b15db02f9d73443435403cbff6e7802/ggml/src/ggml-metal/kernels/argsort.metal#L455), inspected October 9. Related fusion infrastructure landed in [#28948](https://github.com/ggml-org/llama.cpp/pull/28948), merge `5b59b83f4e2101ea173d4f853a0522d9971f48c6`, September 19.

Already included: generic small-expert fusion and generic ADD-chain fusion. Missing: the ten-expert pattern/capacity. Consequently the saving is not automatically ten launches: normal ADD-chain fusion may already combine some additions. Cheapest test: construct the exact `[2560,10,T]` expert outputs and `[1,10,T]` weights for T=1,3,4,5, register the ten-expert pattern in an isolated engine, and prove that it matches with ordinary fusion enabled. Check every affected fixed-size fusion array and pattern bound, not just the `MAX_EXPERTS` define. Compare normal dispatch counts and chained-operation elapsed time. Quality risk is floating-point contraction: stored products plus ordered additions need not equal a contracted FMA loop. Start with explicit product rounding and the same accumulation order; check the initial accumulator against the baseline first-product semantics, including signed zero, NaN and near-cancellation cases. Then require tensor/reference, logits, token, partial-acceptance and cached-continuation parity. No model-weight allocation is needed; intermediate memory can fall.

**2. Consolidate redundant sampling reads.** Benefit: reduce CPU/backend bookkeeping each time a target or helper token is sampled. Local [`common/sampling.cpp:132`](../../vendor/llama-m5-copy/common/sampling.cpp) and `common_sampler_sample` call several exported getters, each of which calls `synchronize()`. [#30196's pinned implementation](https://github.com/ggml-org/llama.cpp/blob/6071ef3c9931d4af1308ac6bd6721cfabb5318e1/common/sampling.cpp), October 9, bundles them into a borrowed view after one synchronization and retains existing sampling math. It is absent locally. The author's CUDA results are not a Metal forecast: after the first real wait, later Metal calls may only check already-completed work.

Cheapest test: count getter/synchronize calls and measure cumulative **CPU duration** with an already-complete context, then a small native decode first-read case. Distinguish redundant calls from actual GPU stalls: Metal clears `cmd_buf_last` after the first wait, so repeated getters are not evidence of repeated live GPU fences. A meaningful first-read test must consume the new view before an old getter has accidentally synchronized it. Keep grammar and CPU fallbacks, multiple output rows and borrowed-pointer lifetime tests. Memory cost is negligible. If redundant calls total less than 0.5% of ordinary response time, retain only if its maintenance/correctness value warrants it; do not expect a TPS win.

**3. Target the BF16 hyper-connection projections by shape.** Benefit: read repeated shared matrices efficiently even when only four tokens are being verified. The actual target tensors are BF16 `[10240,320]` and `[320,10240]`, used by `build_hc_mix` in [`qwen4exp.cpp:314`](../../vendor/llama-m5-copy/src/models/qwen4exp.cpp); the trace sees 97 of each per target graph. The two directions require separate tuning: one reduces a long K=10240 into 320 outputs; the other expands K=320 into 10240 outputs. Their logical stored weights total about 1.18 GiB per target graph, without asserting that every byte is reread from DRAM.

Our four-row BF16 path already uses few-row **simdgroup MMA**, so repeating the old BF16 threshold/tile sweep is not new. The new design reference is [MLX's thin-N kernel](https://github.com/ml-explore/mlx/blob/3c40e8f92d0cce0866fc2f436f9b5096cf3b0ea7/mlx/backend/metal/kernels/steel/gemm/kernels/steel_gemm_thin_nax.h), merge October 8, plus [October 9 thin-M dispatch](https://github.com/ml-explore/mlx/commit/a87691d2de8b6185fdca6b565c755596f3f66df4). It uses register-held inputs, a small TensorOps tile and split K. Its dispatch requires F16/BF16 output, unlike our BF16 weights, F32 activations and F32 result. Its reported thin-M cases use 16-64 rows, not our four/five. Adapt the **design** with the local precision contract; an unchanged import is unsuitable. Also test a conservative exact-shape specialization of the existing MMA path as the control for the new design. Cheapest test: first compile a mixed-type cooperative-input probe with the existing selected Xcode/Metal SDK and explicit availability guards; Tensor API being on does not prove these newer features compile. Then test the two exact matrices, T=1..5, diverse saved/synthetic activations and chained invocations. Keep weights BF16 and outputs F32, allow no persistent converted copy, and verify register/scratch limits. BF16 narrowing of activations would be a separate precision experiment.

**4. Group repeated experts without CPU readback.** Benefit: several tokens using the same expert can share a weight load/dequantization while still doing each token's math. Local `ggml_metal_op_mul_mat_id` uses a matvec path for these sparse four/five-row batches. [#30047](https://github.com/ggml-org/llama.cpp/pull/30047), head `c1d2e51bbeca8cb1d5b0e2cd312e1a3c23bda614`, updated October 7, supplies an active-expert map and MMA implementation, but its average-density gate leaves our 40/512 and 50/512 cases on matvec. Merely backporting it does not implement this experiment.

Construct a tiny GPU map for the at-most-40/50 assignments, dispatch one-appearance experts through the normal kernel and repeated experts through a two-to-five-row reuse kernel. Reuse mapping across gate, up and down. Avoid 512 padded groups or a host readback per layer. Use the saved route distribution and completely distinct/adversarial routes; mapping, gather and scatter time must be included. [MLX's grouped implementation](https://github.com/ml-explore/mlx/blob/99f109b567b969ef06974f1e0450ce0e2eeb4de2/mlx/backend/metal/kernels/quantized_nax.h#L1565), October 9, is a scheduling reference with different quantization/layout, not a Q2_0 port. Its small-group performance reports warn that grouping alone does not ensure a win. No permanent expert cache is proposed. Main risks: routing/scatter errors, quantization semantics, reordered sums and mapping overhead. Kill the prototype if it loses on the actual four-row distribution or only wins with unrealistically repeated IDs.

**5. Pair gate/up and finish SwiGLU before writing intermediate results.** Benefit: use one activation load for both expert projections and avoid a gate/up round trip. Current [`llama-graph.cpp:2241`](../../vendor/llama-m5-copy/src/llama-graph.cpp) constructs separate expert up and gate matmuls; the inspected fusion table has no MUL_MAT_ID-plus-GLU pattern. The stored Q2_0 gate/up tensors share dimensions but occupy separate ranges, so a two-buffer kernel can preserve the model format. The native fork's [resident launcher](https://github.com/liangxiwei/Strata-for-mac/blob/13da72298e0505bdcc4069bd87e96bc11e7b7aa5/src/kernels/metal/iq_kernels.mm#L370), code unchanged since October 4 and refreshed October 9, combines gate/up scheduling but still separately launches SwiGLU, q8_1 activation quantization and down. It does **not** demonstrate a complete fused expert chain.

First adapt only paired gate/up plus the SwiGLU epilogue, with current F32 activation/output semantics and no q8_1 activation conversion. Keep down separate until a measured win justifies further fusion: full gate/up/down fusion can duplicate gate/up calculations across down-output tiles or require expensive barriers. Candidate 1 already addresses the final reduction with much less work. Cheapest test is a complete single-layer path with exact Q2_0 weights and T=1/4/5, including scratch traffic; reject a microbenchmark that times only the matmul. Expect register-pressure and altered sigmoid/rounding risks. Shape-specific down address arithmetic, as in the native fork's canonical 2560x640 kernel, is an additional small ablation, not another established gain.

**6. Keep the full vocabulary and specialize its Q5_K kernel.** Benefit: make the helper's repeated choice among 248,320 tokens cheaper without removing tokens or re-encoding weights. Inventory confirms `output.weight` is Q5_K `[2560,248320]`, 437,043,200 bytes, shared by target/helper. Target few-row MMA is already present; the helper's sequential single-row head uses `kernel_mul_mv_q5_K_f32_impl` in [`mul_mv.metal:1632`](../../vendor/llama-m5-copy/ggml/src/ggml-metal/kernels/mul_mv.metal). [Pinned source](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/ggml/src/ggml-metal/kernels/mul_mv.metal#L1632), October 5 pin, inspected October 9.

Specialize K=2560, use exact Q5_K unpacking, and test two/four output rows per simdgroup with the present reduction order and F32 outputs. Distinguish output-row tiling from batching future helper tokens: those tokens depend on earlier choices and cannot simply be evaluated together. Draft backend top-k sampling is **already enabled**, confirmed by `backend_sampling=1` in the actual native log; do not claim that as a new head optimization. A later fused tile-local top-k would save logits traffic, not the full vocabulary dot products, and must preserve ties/candidate semantics. Cheapest test: exact full-head shape and a downstream top-k step, T=1 versus current kernel and T=4 as regression control. No decoded head cache: a full F16 expansion alone is about 1.18 GiB and would consume much of the observed headroom if retained alongside the quantized head. Precision, tie handling and acceptance must be tested.

**7. Order token/PLE gathers to reduce real scheduler crossings.** Benefit: group CPU embedding preparation before the GPU portion. [#30160](https://github.com/ggml-org/llama.cpp/blob/7f461fd8743d7e47e3d81cafd5fe91e8b6e095a6/src/models/qwen4exp.cpp#L420), October 8-9, directly moves qwen4exp PLE gathering before token embedding construction and changes mixed-input graph ordering. Our saved shape attribution places ordinary token GET_ROWS and lazy PLE on CPU, but this does not prove an avoidable normal-runtime split. Current code already attempts to keep PLE and token embeddings in the same split.

Cheapest test: compare normal scheduler split plans and CPU/GPU boundary counts for target pure-token prompt/verify and helper token-plus-hidden-state inputs; no per-node callback timing. If topology is unchanged on those paths, demote before a full run. The PR still lists unfinished generic-model work, so adapt the minimal qwen4exp-safe portion only after checking dependencies and inactive branches. Preserve token order, PLE history, empty outputs and graph reuse. Memory overhead should be negligible; no table residency change is involved.

**8. Dequantize into cooperative inputs for the prompt path.** Benefit: eliminate the store/reload through threadgroup memory before TensorOps consumes a quantized tile. The local TensorOps `kernel_mul_mm` explicitly dequantizes into `sa`, barriers, calls `mm.run`, then barriers again in [`mul_mm.metal:49`](../../vendor/llama-m5-copy/ggml/src/ggml-metal/kernels/mul_mm.metal). This is different from the short-row simdgroup MMA path already optimized locally. [Apple's WWDC26 session](https://developer.apple.com/videos/play/wwdc2026/330/) documents custom dequantization into cooperative input tensors and the layout-compatibility check; it does not make GGUF Q2_0 a native MX-format operand. macOS 27.2 and an installed Xcode-beta 27.0 were read-only verified; API compilation remains untested in this research.

Start with one quantized dense prompt shape and one exact format, keeping current dequantized precision, scaling and bounds. Only then consider grouped expert prompt matmuls. No full-model format conversion, ANE backend or hardware-occupancy claim is implied. Cheapest test: an isolated compile/API probe, exact tensor correctness, then chained prompt-shaped kernels with existing TensorOps as control. The tradeoff is additional register pressure and potentially lower concurrency; larger tiles can erase the traffic saving. The expected metric is prompt TPS/TTFT, with no presumed gain for the present four-row decode dispatch. Scratch should remain on chip; any unexpected spill/allocation or inaccurate custom dequantization is a stop condition.

**9. Test target backend sampling, keeping the helper's existing offload.** Benefit: reduce CPU vocabulary processing/readback for target verification. In saved requests target `backend_sampling` is false, whereas helper backend sampling is already true. [`server-context.cpp:1925`](../../vendor/llama-m5-copy/tools/server/server-context.cpp) can attach a target sampler; [`llama-context.cpp`](../../vendor/llama-m5-copy/src/llama-context.cpp) decides what outputs to return. [#30223's pinned graph change](https://github.com/ggml-org/llama.cpp/blob/3fd76a33b1616e69fb25856bf531e93e3ebedcfc/src/llama-graph.cpp), October 9, addresses variable output-chain topology under speculative batches. It is a separate candidate from #30196, and their gains overlap.

Cheapest test: a small-model greedy case with the actual sampler chain and backend registration status, followed by four-row speculative sampling and graph-reuse checks. A flag accepted by the parser does not prove offload succeeded. Validate logit biases, grammar fallback, n_probs behavior, every verification row, first reads and output order; ordinary writing with stochastic sampling needs a separate test. The target/helper hidden-state transfer and helper CPU expert crossings remain, so this does not make the whole MTP cycle asynchronous. Extra graph/output memory must be accounted for rather than assumed zero.

**10. Choose short draft lengths from measured cost and accepted-prefix history.** Benefit: spend fewer helper steps in difficult prose while retaining useful larger batches for predictable code. This extends the completed static depth/confidence sweeps; it is not another sweep or a claim that deeper always wins. The saved controls show roughly 41% Chinese, 46% prose and 71% code draft acceptance, with much higher values on short cached fixtures. Local [`common/speculative.cpp:1650`](../../vendor/llama-m5-copy/common/speculative.cpp) iterates helper steps until `params.n_max`, then the server verifies a batch. [Pinned source](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/common/speculative.cpp#L1650), October 5, inspected October 9. The refreshed architectds `best` head `901ebe5267a943d5e99da7220669954c27936511`, October 8, is a different CPU/CUDA scheduler, not an available Mac controller.

A proposed controller should estimate accepted tokens per cycle as `1 + sum(P(accepted prefix >= i))`, then divide by normal measured target-plus-draft cycle time for each allowed depth. Raw acceptance percentage alone is insufficient. Start with {1,2,3}, an adaptation minimum window and a fixed-depth fallback; retain the present three-token rollback budget, including the current state plus its rollback snapshots. Cheapest test: replay existing accepted-prefix and cost traces as a screening simulation, explicitly excluding it as a speed result; only then compare real mixed workloads. Stop if shape churn, graph rebuilding or policy oscillation consumes the predicted saving. Require identical greedy output and unchanged target validation; random sampling/state advancement needs separate distribution/correctness tests.

## Useful conditional ideas, below the main queue

**Command-buffer submission: measure, then try 0/1/2 encoders.** Local Metal initialization sets `n_cb=1`, independently of the helper's eight CPU workers. A small isolated override could test 0/1/2 while preserving graph fusion and threadpool settings. Low/base/high TPS hypothesis is -2/0/2%; negligible persistent memory, small implementation. [Current encoding code](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/ggml/src/ggml-metal/ggml-metal-context.m#L491), October 5 pin. [MLX issue #4521](https://github.com/ml-explore/mlx/issues/4521), September 16, describes a different byte/operation-limit mechanism and is only a motivation to measure CPU submission time. Its environment variables do not apply to llama.cpp. Avoid fusion-stat mode during performance tests: locally it forces `n_cb=0`. Keep only if normal wall time and GPU idle gaps improve; fewer command buffers alone is insufficient.

**Bounded PLE prefetch with more useful lead time.** Low/base/high hypothesis is -1/0/3% decode TPS or -5/0/20% diverse-prompt TPS, conditional on measured native I/O waits. Current `qwen4exp.cpp:1289` already calls `llama_prefetch_rows`; `llama-mmap.cpp:877` uses page-aligned `MADV_WILLNEED`. [#29599](https://github.com/ggml-org/llama.cpp/pull/29599), merged September 30 as `185103dcf53222165ecd15ce8e406606e25bd091`, is already included. Older direct-read [#28136](https://github.com/ggml-org/llama.cpp/pull/28136) and [#29030](https://github.com/ggml-org/llama.cpp/pull/29030) are closed/superseded by it; they are not fresh missing defaults. Also, buffered `pread` is not proof that reads bypass the OS cache.

The genuinely new question is whether known next-prompt rows or completed draft candidates can receive useful advance notice while compute proceeds. Capture file-specific demand waits, page misses, deduplicated rows and prefetch hit/unused-byte counts in the native path first. The existing 6.09 MiB sampled-read fixture does not answer this. Start with a bounded queue and at most tens of MiB of staged/cache data; never pin 28.8 GB. Retain original fetch fallback and token/history identity. Reject if native lookup waits are below 2% of response time, if unrelated/rejected draft reads displace resident weights, or if new swap appears. Repeated-sentence synthetic prompts are especially weak evidence here; use diverse real text with honest cache-state labels.

**GDN row-group specialization, retaining every rollback snapshot.** Low/base/high TPS hypothesis -1/0/2%, low confidence, medium complexity, no persistent memory growth. In [`gated_delta_net.metal`](../../vendor/llama-m5-copy/ggml/src/ggml-metal/kernels/gated_delta_net.metal), `NSG` couples elements per lane with rows per threadgroup; the launcher fixes it to `S_v/32`. A controlled alternative can keep four state elements per lane for S_v=128 while independently trying one/two/four rows per group, preserving current recurrence and fused snapshot destination. The current kernel already holds recurrence state in registers across verification tokens and writes required snapshots directly to cache. There is no duplicate recurrence or large trailing CPY to remove. Test exact K=4, T=1..5, fused/unfused destinations and every partial-acceptance slot; do not drop snapshots or change precision. Stop unless a fusion-preserving trace shows enough normal cost and exact-state microbenchmarks show a repeatable win. [Pinned kernel](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/ggml/src/ggml-metal/kernels/gated_delta_net.metal), October 5.

## The next three experiments, with falsifiable decisions

1. **Ten-expert reduction fusion.** First demonstrate the normal graph pattern is eligible and the new path fires. Run operator cases with 1/3/4/5 rows, near-cancellation values, non-contiguous/aliased fallback and unrelated fusion-boundary cases; require controlled product rounding and correct addition order. Then use fresh stock/candidate/candidate/stock launches at the existing fixed settings. Reject on any unexpected token/state change, new swap or failure to reduce normal dispatches; do not adopt for speed unless fresh writing and complete-reply medians improve by at least 1% across more than one real writing workload and exceed bracket drift. If it only reduces bookkeeping below noise, record that result and stop.
2. **#30196 sampling view.** First measure the repeated synchronization calls' CPU time without per-op graph callbacks. Require first-read, helper top-k, ordinary target CPU sampling and grammar-fallback correctness. Compare it independently of target backend sampling. Reject the performance rationale if removable overhead is below 0.5% or matched whole-reply timing fails to improve beyond drift. Published large CUDA gains are irrelevant to this criterion.
3. **One BF16 shape at a time.** Start with `[10240,320]` and four activation rows, then independently `[320,10240]`. Compare current MMA, a compile-time exact-shape specialization and the MLX-inspired mixed-type TensorOps design, without narrowing F32 inputs. Require at least 10% repeatable chained-operator improvement, no more than 2% regression at adjacent row counts, then at least 2% whole-model fresh-output improvement or a separately valuable prompt-time win. Abort on precision drift, unexpected spills/scratch growth, memory-guard failure or no normal-runtime benefit. Repeating threshold changes already tested does not satisfy this experiment.

For every full-model comparison, preserve all other settings, use fresh bracketing controls, record prompt TPS, sustained writing TPS, TTFT, total reply time, accepted-prefix lengths, output tokens and memory/swap. Include longer real prose/code responses as well as the existing 128-token fixtures; report cached-ledger responses separately. Restore normal fusion for performance comparisons. Operator wins qualify a model trial; they are not model speed evidence.

## Explicitly demoted or already covered

- **#30139 read-in-place:** its `get_rs_in_place()` returns false when `n_rs_seq != 0`. Our target uses three rollback slots. A target-only/no-rollback test or a helper with compatible recurrent state may benefit, but current MTP target benefit is not established. Do not remove that guard to chase the reported result.
- **#30209 FlashAttention 128/96:** refreshed October 9, source head `dff01ea985b5`; current saved model metadata has K/V head sizes 256/256. It is not a kernel for this model's head shape.
- **Quantized KV:** #29340 remains a prerequisite if pursued, but current 8K F16 already passed capacity tests. Saving cache bytes is not automatically a speed improvement, and it changes a quality-relevant precision choice.
- **Full HC fusion, dense re-encoding, vocabulary trimming, full expert paging and ANE conversion:** no new local performance proof. The first three overlap earlier weak/negative or precision-changing experiments; paging addresses capacity with potential latency loss; no inspected ANE implementation handles this exact model path.
- **Native 256K results and fork popularity:** a README update, large-memory result or fork name is not a new applicable optimization. The native resident expert implementation remains valuable source reference, with q8_1 activation and layout differences that must be removed or explicitly treated as separate numerical changes.
- **Blind MLX kernel imports:** [#4631](https://github.com/ml-explore/mlx/issues/4631), October 5, documents precision discrepancies between multirow and gathered affine paths; [#3887](https://github.com/ml-explore/mlx/issues/3887) documents a K-tail failure. These are not bugs in our Q2_0 kernel, but they justify exact stored-weight reference tests, partial tiles and batch-shape coverage in any adaptation. Current MLX source has also evolved beyond those reported versions.

No current evidence supports adding all proposed gains, promising a specific new TPS plateau, or inferring M5 occupancy from model size or Tensor API availability. The first two experiments can settle concrete small questions cheaply; the BF16 and grouped-expert work offers more possible upside with correspondingly more implementation and numerical risk.
