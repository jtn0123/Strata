Smallest proposed axis: an initialization-only private opt-in, default off, eligible only for explicit `cache_prompt=false` text completion on the pinned target/helper setup. Keep all batch construction and checkpoint metadata transitions identical; omit only prompt-reuse payload creation. Keep true requests, missing/default-true policy, child/shared-prefix requests, multimodal/adapter tasks, slot save/load and RAM prompt-cache persistence on the original behavior until separately proven. No split removal, on-device snapshot replacement, rollback change, math/precision change or launcher-default change belongs in stage 1.

**Implementation gate:** skipping `create_checkpoint` changes future splitting. Keeping empty entries without a restore distinction is unsafe. Filtering them and recomputing a later cached request changes its reuse and potentially batch shapes, so that is not proof of unchanged cache-enabled behavior. The missing earlier state cannot be recreated later without retaining a snapshot or replaying work. A bounded all-false, freshly cleared single-slot cohort could establish a serialization-saving ceiling, with identical metadata decisions; it would qualify only that stateless cohort. Do not present it as a general mixed-policy implementation. If preserving false-to-true reuse is mandatory, retain original serialization wherever that future reuse remains possible, or stop this stage pending an explicitly narrower lifetime contract.

Qualification before timing must record actual prompt-checkpoint save calls/bytes and successful omissions separately from speculative save/restore counts. Use compact per-request diagnostic summaries, never tensor callbacks during performance. Compare original and candidate prompt decode tuples (slot, token positions, row count, output flags), checkpoint scheduling metadata, target/helper verification widths, emitted token IDs/text and acceptance/replay outcomes. Cover 48/53-token English tasks, contextual English code/prose around 512/2048 tokens, exact checkpoint-offset boundaries, repeated changed/restored inputs, cancellation/recovery, EOS/output limits and a genuinely exercised rollback. Cover true-to-true, true-to-false and especially false-to-true edited-prefix continuation plus same-prefix reuse. An unexercised restore is not a pass. Require identical behavior for every admitted history; otherwise stop or explicitly reduce scope before timing.

Only after those gates, use fresh original-control/candidate/candidate/original launches, excluded warmup, three measured repeats per English task, 256 output tokens, temperature 0.6/seed 1234 and unchanged packed Q3 helper, mixed placement/eight workers, depth three, Tensor API, F16 KV, 4K context and batch/ubatch 512. Pin source/build/model/harness/request receipts; require zero new swap and exact outputs. Report client first-content TTFT and complete-reply time alongside generation TPS; initial HTTP headers/progress are not first content. Cache-enabled cohorts remain separate.

Predeclare a narrow latency gate: at least 1% TTFT improvement on both real English tasks, each above twice its own absolute control drift; whole reply must improve above its own drift, with no material generation-TPS regression (at least 1% beyond drift). A general TPS claim still requires the ledger's separate at-least-1% TPS **and** whole-reply improvement on both tasks above their own drift. One bounded bracket only; park if either latency task misses the gate, eligibility is absent, parity/lifetime fails or swap grows. Do not chase a smaller threshold afterward.

Savings may be negligible: snapshots may be few, already cheap/resident, dominated by unavoidable GPU completion, or absent under the actual workload; prompt splitting and all model work remain, and a small TTFT saving is diluted across a 256-token reply. Source review therefore recommends resolving lifetime first, then measuring original exposed serialization cost. It does not recommend starting R05 automatically after R03.
